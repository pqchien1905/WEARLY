# Local COD and VNPay refunds implementation plan

> Execute inline with executing-plans, TDD and one independent final review.

**Goal:** Record explicit COD refunds and verified sandbox VNPay refunds without
over-refunding, duplicate sends or treating gateway acknowledgement as settlement.
**Architecture:** Durable source-specific refund ledger, order-locked reservation,
network calls outside transactions, immutable request identity and verified query.
**Tech stack:** NestJS/Prisma/PostgreSQL, existing VNPay HTTPS adapter, Flutter.
**Spec:** docs/superpowers/specs/2026-10-21-local-completion-design.md.
**BASE:** 8e584f5.

## Global constraints and decisions

- Integer VND, local sandbox only, no real money endpoints. Existing receipts and
  payment attempts remain historical evidence. Refunds never change inventory.
- Each paid VNPay attempt is a separate source. Primary is the transaction matching
  Payment.providerTransactionId; extra successful attempts are fully refundable.
  COD source requires an explicit PaymentSettlement. No invented legacy receipt.
- Primary entitlement: full payment including shipping after pre-dispatch cancel
  or carrier RETURNED; otherwise sum of RECEIVED customer return entitlements
  (shipping retained). Free payments have no refundable source. Refunded legacy
  payment without ledger is unavailable for new refunds and needs review.
- Refund creation uses UUID requestKey, expected order version and expected amount.
  It refunds the currently available entitlement for the selected source. Multiple
  partial customer returns produce multiple partial refunds. Pending/unknown/success
  reserve funds; only a verified rejection releases them. No arbitrary overpayment.
- COD creation records actual refund reference, actor, timestamp, amount and audit
  atomically. It is explicit operator confirmation of money returned, never inferred
  from physical return. Duplicate reference cannot create a second receipt.
- VNPay creation persists a unique provider request ID before a single network send.
  Retry returns that row, never resends. Crash/lost response leaves reserved funds
  for review. Signed final00 succeeds,05/06 remain PROCESSING,09 fails; ambiguous or
  invalid responses remain REVIEW. No automatic resend after provider uncertainty.
  Only one unresolved refund per source; response OrderInfo must match the initial
  request-specific description. Further entitlement waits until resolution.
- Query accepts the known refund transaction number, or an operator-supplied refund
  number obtained from sandbox portal. It must differ from original payment number,
  and signed response must match merchant/reference/type/amount/number. Unknown
  result never releases funds. Per-refund query cooldown10s. Query has no money side effect.
- Payment PARTIALLY_REFUNDED reflects successful refunds of primary collection;
  REFUNDED only when primary amount fully returned. Additional collections/refunds
  remain visible separately. Financial report shows gross collected/refunded/net.
  Legacy REFUNDED without receipt is reported as unverified, excluded from determined
  net rather than counted as available money or given a fabricated refund receipt.
- Current admin role is authority; finer finance role comes in staff milestone.

## Review focus

1. Lost response/crash then repeated POST: no second outbound refund (API test).
2. Same-amount sequential partial refunds: old query response cannot settle a new
   refund; compare unique refund transaction number and reject original number.
3. Concurrent create/query/callback/cancel: source limits and primary payment state
   survive order locks; late duplicate payment remains separately refundable.
4. Another user's order/source ID and forged signed payloads: fail closed; no raw
   provider payload, staff IDs or secrets in customer response.
5. Navigation/network uncertainty: frontend reload lists durable pending refunds;
   no UI claim of returned money until SUCCEEDED, no duplicate COD receipt.
